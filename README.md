# Listening Lens

A Snowflake Native App that turns your Spotify listening history into a Streamlit dashboard, with a short AI-generated "taste summary" powered by Snowflake Cortex.

Built as a portfolio demo of the Snowflake Native Apps Framework: application packages, the setup script lifecycle, the references/bind mechanism for consumer-owned data, and Streamlit-in-Snowflake, all running on a personal 30-day trial account with no external cloud storage and no Marketplace listing required.

Design rationale and options considered are in [`docs/adr/0001-architecture.md`](docs/adr/0001-architecture.md). Scope and requirements are in [`docs/requirements.md`](docs/requirements.md), and how the pieces fit together is in [`docs/solution-design.md`](docs/solution-design.md).

## What it does

- **Trends tab:** top artists over a real date window, a listening-by-hour-of-day chart in the listener's local time, longest listening streaks, and a drill-through: pick an artist from the top-artists chart to see the real underlying play rows behind it. A genre breakdown would be here too, but Spotify's genre data for this account currently comes back empty; see `docs/requirements.md` OQ-3 for why.
- **Discover tab:** a short natural-language summary of your listening taste, plus a "You might also like" section naming specific artists you likely haven't heard yet with a one-line reason each, both generated by Cortex `COMPLETE` over aggregated stats (not raw personal data).
- **Bring your own data (optional):** the app defines a Native App reference so a consumer can point it at their own listening-history table instead of the bundled sample, using Snowflake's `reference()` table function to query it without needing broader database/schema access. Built and confirmed live, bind and unbind; demonstrated separately from the main demo path, see the ADR for why.

## Quick start

> Prerequisites: a Snowflake account (Enterprise edition or higher, a region with direct Cortex model support), the Snowflake CLI, Python 3.10+, a Spotify Developer account.

1. Clone this repo.
2. Run [`scripts/bootstrap_account.sql`](scripts/bootstrap_account.sql) once against your Snowflake account (role, warehouse, and the privileges needed to build and install a Native App without a Marketplace listing).
3. Add a `snow` CLI connection profile pointing at that account. This is local config, not part of the repo.
4. `pip install -r scripts/requirements.txt`
5. Copy `.env.example` to `.env`, fill in your Spotify Developer app's client ID/secret.
6. `python scripts/pull_spotify_data.py`: pulls your recently-played and top-items data, writes `data/listening_history.csv`. If you've already requested Spotify's Extended Streaming History export from your account's privacy settings and it has arrived, run `python scripts/parse_extended_history.py path/to/export.zip` instead: same output file, no API auth needed, real multi-year history instead of a ~50-play window.
7. `snow app run`: builds the application package, uploads artifacts, creates the app in your account.
8. Run [`scripts/grant_cortex_access.sql`](scripts/grant_cortex_access.sql) once against your account (as `ACCOUNTADMIN` or another role with `MANAGE GRANTS`). The manifest's `snowflake_database` block only declares that the app wants Cortex access, it doesn't grant it, this is the separate consumer-side step that actually does.
9. Open the app from Snowsight (Apps, then Listening Lens) to reach the Streamlit page.

## Why these choices

- **Bundled sample data, with an optional reference for bring-your-own data.** The app always has something to show without depending on Spotify's data-export queue (which can take up to 30 days). The reference path still exists and is demonstrated, because it's the more advanced half of the framework and the more interesting thing to talk about in an interview.
- **Cortex `COMPLETE` for the summary, not a custom model.** The point of this demo is the Native Apps Framework, not model training. Cortex keeps the AI feature honest: a few lines of SQL, not a project in itself.
- **No external cloud storage, no Marketplace listing.** Provider and consumer are the same account, which is the supported local-testing path in current Snowflake docs and removes an entire review/approval process that isn't the point of this demo.

## What this demonstrates

Application package lifecycle (`CREATE APPLICATION PACKAGE`, versioning, `CREATE APPLICATION ... USING VERSION`), the manifest and setup script contract, application roles and privilege grants, the references/bind pattern for consumer-owned data, and Streamlit running inside a Native App rather than as a standalone Streamlit app.

## Redeploying to a new trial account

Nothing here is tied to one Snowflake account. If a 30-day trial expires or a fresh one is cleaner for any reason:

1. Sign up for a new trial, Enterprise edition, in a region with direct Cortex model support (see the ADR).
2. Run `scripts/bootstrap_account.sql` against it. It grants the role to whoever runs it, so there's nothing to edit first.
3. Add a new `snow` CLI connection profile for it.
4. Re-run `scripts/pull_spotify_data.py` (Spotify data isn't tied to the Snowflake account, and isn't committed to the repo anyway).
5. `snow app run`.
6. Run `scripts/grant_cortex_access.sql` against the new account.

Everything that defines the app (manifest, setup script, Streamlit code, project config) lives in this repo, so the account itself is disposable.

## Status

Core demo (Phase 1) complete and confirmed live end to end against a real trial account, both tabs, with real personal data.

`snow app run` installs cleanly, the Trends tab renders real data (ten top artists, an hour-of-day distribution, a 4-day streak, all matching the actual pulled Spotify history), and the Discover tab generates a real Cortex taste summary. Getting there surfaced two genuine gaps along the way, both resolved: the manifest's `snowflake_database: roles: - CORTEX_USER` block declares intent but doesn't grant the role (fixed with `scripts/grant_cortex_access.sql`, now part of the standard install steps above), and Snowflake's trial-account policy separately blocks Cortex AI function calls outright without a payment method on file, an account-tier restriction with no code workaround (fixed by adding a payment method). Full narrative, including every error message hit along the way, is in [`docs/build-log.md`](docs/build-log.md).

Update, 2026-09-13: Spotify's Extended Streaming History export arrived and was pulled into scope early (FR-7, was Phase 2/future). `scripts/parse_extended_history.py` parses it into the same schema `pull_spotify_data.py` produces: 42,366 real counted plays from 2018 to 2026, after dropping podcast rows and plays under a 30-second threshold (details in `docs/solution-design.md` section 6). Loading it surfaced two real bugs, both found and fixed the same day: `setup_script.sql` was appending instead of replacing data on every upgrade, and the Trends/Discover queries in `streamlit/listening_lens.py` were still hardcoded to sources that predated FR-7, so the new rows loaded but were never actually read. Confirmed live after both fixes: exactly 42,366 rows loaded, an 87-day longest streak, Discover tab working correctly at this scale. Full narrative in `docs/build-log.md`.

Update, 2026-10-07: the history now excludes household listening that isn't the account holder's own taste (a nightly children's bedtime album), via `parse_extended_history.py`'s new `--exclude-artist` flag, leaving 40,874 counted plays. Hour of day and the streak are now computed in local time rather than raw UTC, and Top artists is sorted by play count. Confirmed live the same day: 40,874 plays, a 70-day longest streak, and the Discover tab's top five no longer skewed by the excluded album. Details in `docs/build-log.md`.

Update, 2026-09-13 (same day): the consumer reference/bind path (FR-6) is built and confirmed live, bind and unbind, along with a new artist drill-through in the Trends tab. Getting the bind working surfaced two more real issues: a `GRANT MONITOR` was mistaken for `GRANT USAGE` on the consumer side, and this app's own first version queried the bound table by literal name instead of Snowflake's `reference()` table function, which is the only way to read through a reference without broader database/schema access. Full narrative, including both fixes, in `docs/build-log.md`.
