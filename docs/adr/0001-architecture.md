# ADR-0001: Listening Lens, a Snowflake Native App for personal listening analytics

**Status:** Proposed
**Date:** 2026-09-11
**Deciders:** Jay (solo build)

## Context

This demo was built to get hands-on with the Snowflake Native Apps Framework, in particular the references and bind mechanism for consumer-owned data. The constraint set is deliberately tight:

- Solo build, evenings and weekends, target is days, not weeks.
- Runs entirely on a personal 30-day Enterprise-edition trial account. No employer data, no employer tooling, nothing that ties back to the day job.
- Provider and consumer are both the same account and the same person, so no Marketplace listing, review, or approval is needed. Confirmed against current Snowflake docs: local install and test is fully supported without publishing.
- The build should read as a genuine engineering artifact, not a tutorial retyped. A generic cost-governance or RBAC-audit app is the obvious choice for this framework; a demo tied to something he actually cares about (music) is more memorable and a more natural story to tell.

Two data-source constraints shaped the decision below:

1. Spotify's official data export ("Extended Streaming History," requested from the account privacy settings) can take up to 30 days to arrive. That is not compatible with a days-not-weeks timeline if it is the only data source.
2. The Spotify Web API's "recently played" endpoint returns at most the last 50 tracks, requires the `user-read-recently-played` OAuth scope, and is usable immediately for the developer's own account in Development Mode, with no app review needed for personal use. Depth is thin but availability is instant.

## Decision

Build **Listening Lens**: a Native App with one Streamlit-in-app page, backed by a small SQL/Snowpark layer, that analyzes listening history and produces a short natural-language "taste summary" using Cortex `COMPLETE`.

Data strategy (see Option analysis below): bundle a working sample dataset pulled from the Spotify Web API so the app is fully functional out of the box, and define one Native App **reference** so a consumer can optionally point the app at their own listening-history table instead. This means the live demo never depends on data that might not have arrived yet, while the architecture still demonstrates the reference/bind pattern, which is the more advanced and more substantial half of the Native Apps Framework story.

Application structure:

- `manifest.yml` (`manifest_version: 2`): declares `setup_script`, `readme`, `default_streamlit_app`, one `references` entry (`listening_history_ref`, optional, bind to a consumer table), and a `privileges` block (each privilege carries a `description`, which the framework requires).
- `setup_script.sql`: creates the application role, a `core` schema, the reference definition, the bundled sample tables (loaded from a stage at install time), and the Streamlit object; grants `USAGE` on all of it to the application role.
- `streamlit/listening_lens.py`: two tabs.
  - **Trends**: top artists and genres over time, a listening-by-hour-of-day heatmap, longest streaks. Plain SQL aggregation, no ML.
  - **Discover**: a short natural-language summary of listening taste and a handful of suggested directions to explore, generated by feeding aggregated stats (not raw personal data) into Cortex `COMPLETE`.
- Sample data pipeline (outside the app, one-time): a small Python script against the Spotify Web API pulls recently-played tracks plus short/medium/long-term top artists and tracks, flattens them to CSV, and stages them for the setup script to load.

Trial account setup: create the account in a region with direct Cortex model support (AWS us-west-2 or us-east-1, or Azure eastus2) rather than a region that needs cross-region inference, to remove one moving part before the demo is recorded.

## Options Considered

### Option A: Bundled sample data only, no reference

| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Build time | Fastest, true "days" |
| Risk | Lowest, nothing depends on consumer setup |
| Technical depth | Weaker, skips the reference/bind mechanism entirely |

**Pros:** simplest possible setup script, nothing to go wrong live.
**Cons:** looks like a personal script wrapped in a Streamlit page, not a demonstration of the parts of the framework a real ISV app would use.

### Option B: Reference only, consumer must supply their own table

| Dimension | Assessment |
|---|---|
| Complexity | Medium |
| Build time | Same as A once the reference plumbing exists |
| Risk | Higher for a recorded demo: nothing to show until a table exists and is populated |
| Technical depth | Strongest on paper, closest to a real Marketplace-style app |

**Pros:** most realistic architecture, the pattern most SE demos to prospects actually use.
**Cons:** brittle for a one-take recording; requires setting up and loading a demo table before every run-through, with no fallback if that step fails on camera.

### Option C: Hybrid, bundled data plus an optional reference (chosen)

| Dimension | Assessment |
|---|---|
| Complexity | Medium |
| Build time | One extra day over Option A for the reference definition and a toggle in the Streamlit page |
| Risk | Low: the bundled path always works, the reference path is demonstrated separately and can be re-recorded in isolation if it misbehaves |
| Technical depth | Same technical talking point as B, without B's live-demo fragility |

**Pros:** the app always has something to show, and the harder feature (references) is still built and demonstrable, just not load-bearing for the main recording.
**Cons:** slightly more setup script and manifest surface area than a single-path app; worth it here because the whole point of this demo is to touch the parts of the framework that the Iceberg demo does not.

## Data Source Decision

| Source | Availability | Depth | Decision |
|---|---|---|---|
| Extended Streaming History export | Up to 30 days | Full history, years | Request it now anyway, in parallel, at zero cost. Treat as a bonus upgrade to the bundled dataset if it lands before the recording. Not a dependency. |
| Spotify Web API (recently played, top artists/tracks) | Immediate | Thin (last ~50 plays, plus rolling top-items windows) | Primary source. Enough to build and demo Trends and Discover convincingly. |

Practical note: a personal Spotify Developer app in Development Mode can call these endpoints against the developer's own account immediately, without Spotify's app review, which only gates apps that need access to other users' accounts.

## Consequences

- **Easier:** the account itself is disposable. Everything that defines the app (manifest, setup script, Streamlit code, project config) lives in the repo, and `scripts/bootstrap_account.sql` captures the one-time role/warehouse/privilege setup, so a new trial account is a redeploy target, not a rebuild. See the README's "Redeploying to a new trial account" section.
- **Easier:** the build is not blocked by anything outside Jay's control (Spotify's export queue, Marketplace review). Everything needed to finish is already available today.
- **Easier:** the demo recording has a guaranteed-working path (bundled data) and an optional deeper cut (reference) that can be attempted and re-recorded separately without risking the main take.
- **Harder:** two data paths means the setup script and manifest carry a bit more surface area than the Iceberg demo's single-path design. Worth calling out explicitly in the README so it reads as a deliberate choice, not scope creep.
- **Revisited 2026-09-12, and more serious than assumed, then resolved the same day:** the risk wasn't Cortex credit, it was Cortex being blocked outright. Snowflake's trial-account policy rejects `COMPLETE` calls entirely without a payment method on file, confirmed against Snowflake's own trial-account documentation after a live `Unknown user-defined function` error turned out not to be a manifest/grant problem. Fix: added a payment method to the trial account (converts to paid without ending the trial period or its free credit balance, per the same docs). Confirmed live afterward that `COMPLETE` succeeds and `llama3.1-8b` is available in this account's region. See `docs/build-log.md` for the full diagnosis.
- **Revisited 2026-09-13, scope reopened on purpose:** FR-7 (Extended Streaming History ingestion) was scoped as P2/future above specifically because the export could take up to 30 days, longer than this build's days-not-weeks timeline. It arrived on 2026-09-13, before the demo was recorded, so that constraint no longer applies. Decision: build the ingestion now and load real multi-year history (42,366 counted plays, 2018 to 2026, after filtering) instead of recording with the thinner 330-row API sample. This is a deliberate scope reopening, not scope creep: the original decision was conditioned on the export being unavailable in time, and that condition changed. It also surfaced a data-quality decision the original design didn't anticipate: nearly two-thirds of raw play events in the export were under 30 seconds long, which needed a real threshold call, not just a parser. See `docs/build-log.md` for the full narrative and `docs/solution-design.md` section 6 for the schema and threshold reasoning.
- **Revisited 2026-09-13, same day: FR-6 (reference/bind) built and confirmed, plus an unplanned UI addition.** With the data now at a much more convincing scale (42,366 real plays), decided the app was worth finishing properly rather than shipping it as read-only: built the reference/bind path (Option C's deferred half) and added an artist drill-through to the Trends tab in the same pass, since testing the bind made the lack of one obvious. Both are confirmed live, bind and unbind. Two real issues surfaced building this, both instructive: a `GRANT MONITOR ON DATABASE` was mistaken for `GRANT USAGE ON DATABASE` (MONITOR only permits metadata visibility, not traversal), and this app's own first version queried the bound table by literal name (`IDENTIFIER('db.schema.table')`), which fails because the application has no general database/schema USAGE, only the specific privilege the reference itself captures; the fix was Snowflake's documented `reference()` table function. Full diagnosis in `docs/build-log.md`, 2026-09-13 entry.
